# Grok 多代理全流程施工手册

版本：2026-10-30。目标：从现有基础骨架完成P0后端，按证据持续推进；UI后续交给Codex。用户已指定Codex负责产品/架构、文档裁决与验收监督，Grok负责实际产品代码、调试、测试和唯一代码集成。开发中一般实现选择可自主决策，不逐步等待用户批准。

## 1 启动条件与真实能力预检

在可配置Grok且实际提供工作区文件和终端的编码宿主中打开项目。普通Grok网页聊天不能仅靠提示词获得D盘访问。本文不假设任何特定Grok CLI、插件、参数或IDE功能存在。

第一轮先执行最小只读预检，并将实际结果写入workpool/SESSION.md：

| 能力 | 要验证的事实 | 缺少时的处理 |
| --- | --- | --- |
| 工作区文件 | 能读取AGENTS、BOARD、当前源码；新建施工记录可写 | 无本地工具则停止本地施工，说明缺少哪种宿主能力 |
| 终端 | 能运行命令并取得真实退出码、工作目录与日志 | 不能以拟写命令充当实跑结果 |
| 子代理 | 有真实创建、消息、等待/收取结果、取消能力 | 有终端但无子代理时顺序施工，并写单代理顺序执行 |
| 并发槽 | 宿主允许的活动代理数、是否共享目录 | 按实际槽位降配，默认最多主控加3子代理 |
| 持续执行 | 当前会话/进程是否可持续，是否有可核实后台工具 | 无后台时只承诺当前会话内循环；中断留游标 |
| 依赖与工具 | Python/锁定环境/转换器是否存在 | 缺依赖先诊断与隔离安装；真实模型/转换器缺失单列待验 |

真正创建子代理后记录宿主返回的ID与任务、文件owner；创建失败不能编造ID、并行消息或审查完成。探测不是索要重复开工许可；已经具备的能力立即使用。

## 2 阅读与基线确认

按顺序读AGENTS、当前施工基线、BOARD、施工00/01/02、自己任务合同、总控提示词。确认T01 done仅为G0基础范围，T02生产认证隔离未实现，T02/T03 ready。历史66项基础测试不证明业务链完成。

检查Git实际状态、未提交/暂存改动与文件哈希。当前交付没有初始commit，不能假定worktree已经可用，也不虚构Git用户名/邮箱。若本机已配置真实身份，可按既有规则建立正常基线提交；身份不可得时使用本轮文件哈希快照和单文件owner继续，共享目录不阻止施工。不要覆盖未知改动或重置用户工作树。

先运行与当前基线相符的基础验证。测试数据/缓存均进当天施工目录，不指向var、旧D/E项目或真实资料。模型关闭、默认不跑live_model。发现基线失败先分出诊断，不据旧日志直接标通过。

## 3 开发代理组织

默认四个活动槽：

| 槽位 | 职责 | 写入约束 |
| --- | --- | --- |
| Grok主控兼代码集成 | 排序/认领、共享合同、迁移顺序、集成回归、done判定 | 独占入口、公共schema、注册、迁移、依赖锁与工作池集成状态 |
| 开发A | 第一波T02身份权限；后续按ready任务转岗 | 精确认领自己的模块/测试，禁止改共享文件 |
| 开发B | 第一波T03领域；后续可转资产/Worker/智能体 | 与A不重叠，迁移提交明确提案给主控 |
| 独立审查 | 只读代码/合同、竞态/权限/失败反例 | 不修改被审实现；意见回给owner修复 |

四个开发槽位与产品单个AgentRun最多三职责是不同限制。宿主不足四槽就降为两个开发轮换审查或顺序角色，不能假称真实并行。主控可按风险调整分工和任务粒度，以完成目标为准，不把角色表当僵硬流程。

## 4 首波合同冻结与派工

先让T02/T03并行阅读并提出方案，写入各自不同的提案文件；这一阶段只读公共代码。Grok主控统一形成 `workpool/handoffs/T02_T03_SHARED_CONTRACT.md`，至少明确：

- Principal身份、稳定ID、动作枚举、作用域和授权接口。
- 项目成员/对象ACL表的owner、FK与项目隔离规则。
- 会话生命周期、生产身份隔离、统一错误码与安全投影。
- 哪些配置/模型/入口由集成owner统一修改，各开发可写哪些精确文件。
- 迁移单一head和消费者测试入口；接口变更如何通知下游。

主控采纳并记录合同版本后，才派两路实现。共享合同可以由主控自主解决常规工程细节；核心产品语义或不可逆数据决策超出权限时才升级。不要通过让用户选择每个函数/表名来阻塞开发。

T02/T03交接并集成后进入T04；再并行T05资产与T06持久任务，开工前冻结派生任务信封。T07依赖T05；T08依赖T06/T07；T09依赖T04/T08；T10/T11按50的DAG推进。T11可提前准备故障夹具，但最终验收须等待真实整链。

## 5 自动推进循环

对每个ready增量持续执行：认领与文件owner → 明确可观测目标 → 实现 → 真实自测 → 独立只读审查 → owner修复 → 主控集成复测 → 交接 → 更新BOARD并解锁下游。

一个任务不是一口气写完全部代码再测试。主控按可运行增量安排提交/快照和回归，保留真正失败复现与实际退出码。审查者的自然语言判断不能替代测试；测试通过也不能替代未检查的权限/版本边界。

每次失败记录现象、证据、假设与下一次只改变哪个条件。同一失败连续三次无新证据，转04诊断提示：缩小复现、检查上游合同、查官方资料、必要时更换owner；不是重复相同命令到次数耗尽。只阻断依赖该条件的任务，其他ready任务继续。

除核心产品决策、未授权外发/付费/破坏性数据操作外，例行实现、重构、测试和修依赖自行推进。产品中候选人工确认是产品行为，不能误解为开发每一步必须让用户审批。

## 6 必须重点守住的实现边界

- 当前权限统一用于工具、外发、SSE、下载、导出、候选和回执重放；身份/授权不能用callback占位假装完成。
- 草稿CAS、候选一次消费、业务对象、Audit、Outbox与回执同一短事务；业务不靠进程内锁维持正确。
- 模型/网络/转换在事务外；历史查看不写HEAD；页版和原件不可覆盖。
- StoredObject generation、reservation/pin、GC claim与最终短原子安装遵循06；旧GC/迟到上传不得破坏有效新代。
- Job claim/renew/finalize验证owner、fence、期限与输入；至少一次投递、消费者幂等，不宣称跨系统恰好一次。
- 自动建议偏好归T06/T08，绑定受限actor和preference_revision；运行中关闭/改范围停止旧自动外发与发布；手动运行分开。
- 每个AgentRun最多三职责；运行初始快照固定、实际读取追加账本；角色输出独立，依赖就绪再执行，晚到不覆盖候选。
- 候选编辑先预览，服务器绑定user_patch/effective_proposal、actor、来源/草稿修订、access_epoch/hash/到期；提交只引用保存的preview。

细则按03–07，不在代码里暗改产品语义或安全不变量。必要公共合同变更先记ADR，新编号从ADR-004起，随后同步消费者与回归。

## 7 中断恢复与可恢复游标

每个增量、交接或诊断点更新SESSION，至少记录模式/能力、当前集成owner、基线提交或快照、活动任务/真实agent ID/文件范围、实际进程或终端会话、最后命令/退出码/日志、未解决审查项、阻塞原因、下一条具体动作。

恢复时读取SESSION与BOARD，重新核实进程/代理是否存活、文件是否变化；历史ID不代表仍在运行。重新认领后从最小验证继续，不自动重跑已经提交的业务操作。宿主或模型配额中断时留下游标，不能保证无人唤醒时仍继续执行。

## 8 结束条件与交付口径

持续工作直到P0要求全部实证通过，或所有可推进任务都需要明确外部条件；遇到单个blocked不结束其他ready工作。最终按三类分别报告：

1. 工程功能与G0–G4的实际门禁、并发/撤权/恢复证据。
2. DeepSeek真实烟测、真实用量和模型对照质量评估；缺密钥/授权时标未运行，FakeProvider不能代替它们。
3. UI：本阶段明确未制作，只交OpenAPI、对象/错误/事件Schema、夹具和剩余限制。

不能因文档完整、基础66项通过或模型自评就宣布完整P0完成；验收要求内仍待运行的条目保留状态。报告包含启动/迁移/测试命令、退出码、证据路径、schema/依赖版本、实际未验证项与下一步，不写“基本完成”。
